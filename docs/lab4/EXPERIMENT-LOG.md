## Эксперимент 2. Остановка replica

| Шаг | Команда или действие | Наблюдение приложения | Наблюдение БД |
|---:|---|---|---|
| 1 | Остановить replica (`docker compose stop replica`) | Приложение (пишет раз в секунду) продолжает работать без ошибок | `pg_stat_replication` на primary: 0 подключённых реплик |
| 2 | Выполнить запись на primary | Записи проходят, за время опыта 18 успешных, 0 ошибок | новая проба записана на primary (`sql/02-create-probe.sql`), `sql/01-primary-status.sql`: реплик нет |
| 3 | Запустить replica | Приложение не замечает перезапуска | replica поднялась и подключилась к primary сама |
| 4 | Проверить догон реплики | — | `state = streaming` (`sql/03-replica-status.sql`); `sql/05-integrity-check.sql`: число проб на primary и replica совпадает (21 = 21) |

Вывод: падение replica не влияет на приложение; после возврата replica догоняет без вмешательства. Ограничение: шаблон не использует слот репликации, WAL для отсутствующей реплики хранится в пределах `wal_keep_size = 256MB`; при более долгом простое replica придётся пересоздавать (см. runbook, раздел 1).

## Эксперимент 3. Остановка primary

| Шаг | Команда или действие | Наблюдение приложения | Наблюдение БД |
|---:|---|---|---|
| 1 | Остановить primary (`docker compose kill primary`, аварийное завершение) | Первая ошибка в 10:15:08: `Connection refused`; запись невозможна | `pg_isready`: `no response` |
| 2 | Проверить запись | Все попытки записи не проходят (replica для записи не годится) | replica: `pg_is_in_recovery = t`, связь с primary: `нет соединения` |
| 3 | Проверить чтение replica | Чтение с replica работает | данные на replica доступны (3 000 000 рейсов) |
| 4 | Восстановить: `pg_promote()` на replica | Приложение само переключилось на новый primary: первая успешная запись в 10:15:13 (простой 5,5 с, из них ~5 с сознательное «обнаружение»); id записей продолжается (25 → 36) | replica стала primary (`sql/01-primary-status.sql`: `is_in_recovery = f`); запись от приложения проходит; `sql/05-integrity-check.sql`: дубликатов проб нет, ограничения на месте |
| 5 | Вернуть старый primary и проверить репликацию | Приложение работало без остановки | старый primary пересобран как replica нового: `sql/03-replica-status.sql` на старом primary: `is_in_recovery = t`, `streaming`; `sql/01-primary-status.sql` на новом primary: узел в `pg_stat_replication`, LSN совпадают |

Потеря данных: последняя запись, подтверждённая приложением на старом primary, `id=25`, максимум на новом primary `id=39` → потеряно записей: **0** (лаг репликации был около миллисекунды). RPO при асинхронной репликации не гарантирован нулём; в этом опыте равен 0. Грубая оценка RTO — около 6 секунд при ручном `pg_promote` и автоматическом переподключении приложения.

## Эксперимент 4. Backup и restore

| Шаг | Команда или действие | Ожидаемый результат | Фактический результат |
|---:|---|---|---|
| 1 | Создать backup (`pg_dump --format=custom`, роли отдельно без паролей) | Архив создан | `course_app.dump`, 3,5 МБ; `globals.sql` с 4 ролями без паролей |
| 2 | Проверить архив (`pg_restore --list`) | Список объектов читается | 99 объектов в оглавлении |
| 3 | Запустить чистый restore-узел (профиль `restore`, порт 55434) | Узел healthy | запущен, таблиц до восстановления: 0 |
| 4 | Восстановить архив (сначала роли, потом `pg_restore`) | Ошибок нет | завершено без ошибок |
| 5 | Проверить данные и ограничения | Проверки пройдены | проба `sql/05-integrity-check.sql` на оригинале и копии совпала; число строк в routes, vehicles, trips, incidents совпало; контрольная сумма данных совпала |

Замечание, найденное в ходе работы: первая попытка восстановления без предварительного создания ролей завершилась ошибками для 3 политик RLS (роли хранятся на уровне кластера и в дамп БД не входят). Поэтому порядок «сначала роли, потом данные» закреплён в скрипте и в runbook.

## Итоги и обнаруженные ограничения

- Репликация настроена по шаблону и проверена в обоих направлениях: изменения идут с primary на replica, запись на replica запрещена.
- Остановка replica безопасна для приложения; остановка primary требует переключения (promote), приложение с несколькими адресами в строке подключения переключается само.
- Репликация асинхронная: при аварии возможна потеря последних записей (в опыте — 0).
- Администратор в шаблоне является суперпользователем (так задаёт `POSTGRES_USER`); приложение и аналитик — обычные роли без привилегий.
- Не выполнено: PITR и полностью автоматическое переключение (авто-promote без участия человека).
- Миграция ролей с паролем в открытом виде и `backup.dump` в корне репозитория удалены из ветки (см. `secrets.md`).
