# Спринт 4. Доступы, резервное копирование, репликация и восстановление PostgreSQL

Проект: система мониторинга общественного транспорта (`trans-pulse`). Стенд поднят из шаблона преподавателя `lab4/EXPERIMENT-TEMPLATE` (PostgreSQL 17, primary + replica, асинхронная потоковая репликация). В шаблоне исправлена заглушка `wal_level`, добавлены SSL, аудит и политики RLS. На стенд загружена схема и данные ЛР3. Все эксперименты воспроизводятся командой `lab4/EXPERIMENT-TEMPLATE/scripts/run_all.sh`; исходный вывод — в `lab4/EXPERIMENT-TEMPLATE/results/`.

---

# 1. Роли и права

| Роль | Назначение | Права |
|---|---|---|
| `course_admin` | администратор | суперпользователь кластера (создаёт `POSTGRES_USER` шаблона): структура, роли, журнал аудита |
| `course_app` | приложение | `NOSUPERUSER`, `NOCREATEROLE`; чтение и запись данных; без DDL, без `TRUNCATE`, без `DELETE` по `incidents`, без доступа к журналу аудита |
| `course_analyst` | аналитик | только `SELECT`; столбец `users.password_hash` недоступен (права на столбцы); подключается к replica |
| `replicator` | служебная | только репликация |

**Приложению запрещено подключаться с правами суперпользователя:** оно использует только `course_app` (флаг `rolsuper = f`), пароль администратора ему не передаётся. Привилегированные операции от его имени отклоняются: `CREATE ROLE … SUPERUSER`, `ALTER SYSTEM`, `COPY … TO PROGRAM`, чтение файлов сервера.

Разрешённые и запрещённые операции для каждой роли показаны в `results/01_roles.txt` (около 30 проверок). Примеры:

| Операция | `course_app` | `course_analyst` | `course_admin` |
|---|---|---|---|
| `SELECT` из таблиц | разрешено | разрешено | разрешено |
| `INSERT` / `UPDATE` данных | разрешено | запрещено | разрешено |
| `DROP TABLE`, `TRUNCATE`, `ALTER TABLE` | запрещено | запрещено | разрешено |
| `CREATE ROLE`, `ALTER SYSTEM` | запрещено | запрещено | разрешено |
| `SELECT password_hash FROM users` | разрешено | **запрещено** | разрешено |
| Чтение `audit_log` | запрещено | запрещено | разрешено |

Где настроено: роли — `primary/init/01-initialize-cluster.sh` (из шаблона); права на таблицы проекта, столбцы, RLS и аудит — `sql/10-post-migration.sql`.

# 2. Секреты

Пароли в репозиторий не попадают: в git лежит только `.env.example`, настоящий `.env` создаётся скриптом со случайными паролями и исключён через `.gitignore`; резервные копии тоже вне git. Подробная инструкция — `docs/lab4/secrets.md`.

# 3. Резервная копия и восстановление в чистый экземпляр

Скрипт `scripts/backup_restore.sh`: `pg_dump` (формат custom) с primary → чистый узел `restore` из шаблона (порт 55434) → создание ролей → `pg_restore`.

| Проверка | Результат |
|---|---|
| Архив | 3,5 МБ, 99 объектов в оглавлении |
| Чистый узел до восстановления | таблиц: 0 |
| Восстановление | без ошибок |
| Число строк (9 таблиц) | совпало во всех |
| Контрольная сумма данных (рейсы и инциденты) | совпала |
| Внешние ключи, RLS-политики, владелец | 6 из 6, 3 политики, `course_admin` |

Найденная особенность: роли в дамп БД не входят, поэтому без предварительного создания ролей политики RLS не восстанавливаются. Файл ролей создаётся отдельно и без паролей.

# 4. Репликация: конфигурация и подтверждение направления

Конфигурация — `compose.yaml` (параметры `wal_level=replica`, `max_wal_senders`, `wal_keep_size`, `hot_standby`), создание реплики через `pg_basebackup` — `replica/replica-entrypoint.sh`, пользователь репликации и правило `pg_hba` — `primary/init/01-initialize-cluster.sh`.

Подтверждение (`results/03_replication.txt`, пробы шаблона `sql/01–05`):
- primary: `pg_is_in_recovery = f`, replica: `t`; на primary `pg_stat_replication` — `streaming`, `async`.
- Запись пробы на primary от имени приложения → через секунду та же запись прочитана на replica.
- Запись на replica отклонена: `cannot execute INSERT in a read-only transaction`.
- Число строк во всех таблицах совпадает на обоих узлах.

# 5. Эксперименты с отказами

Приложение имитирует скрипт, пишущий в БД раз в секунду. Строка подключения содержит оба сервера (`target_session_attrs=read-write`): приложение само находит узел, принимающий запись. Подробный журнал — `docs/lab4/EXPERIMENT-LOG.md`.

| Эксперимент | Поведение приложения | Действия по восстановлению | Результат |
|---|---|---|---|
| Остановка replica | без ошибок (20 записей OK, 0 FAIL) | запуск replica | догнала, `streaming`, `replay_lag ≈ 0,9 мс`, строки совпадают (22 = 22) |
| Остановка primary (аварийно) | ошибки записи с 19:40:27, простой 5,6 с (из них ~5 с «обнаружение») | `pg_promote()` на replica; приложение переключилось само | потеряно записей: 0; данные и ограничения целы; старый primary пересобран как replica нового |

# 7. Дополнительные пункты («желательно»)

| Пункт | Что сделано | Результат |
|---|---|---|
| RLS | на `incidents`: диспетчер закрывает инцидент только от своего имени (`app.user_id`), нельзя создать сразу закрытый инцидент или изменить закрытый | чужое имя, отсутствие пользователя, создание закрытого отклоняются (ошибка политики); изменение закрытого затрагивает 0 строк; закрытие от своего имени проходит |
| SSL | сертификат создаётся при инициализации, правило `hostnossl … reject` | `sslmode=disable` отклонён (`pg_hba.conf rejects connection … no encryption`), `sslmode=require` работает, `ssl = true` |
| Replication lag | массовая загрузка 3 млн рейсов на primary, замеры каждые 0,5 с | макс. отставание 42,4 МБ, среднее 7,2 МБ, макс. `replay_lag` 0,30 с; через 0 с после конца загрузки replica догнала (3 000 000 = 3 000 000) |
| Аналитика на replica | аналитик подключается только к replica | отчёты ЛР3 (Q1, Q5) выполняются за 71 и 166 мс, запись отклоняется, сессий аналитика на primary 0 |
| Аудит | триггеры пишут в `audit_log`: смена статуса автобуса, отмена рейса, закрытие инцидента (кто, когда, что было и стало) | записи видны администратору; приложение журнал изменить и удалить не может |

# 8. Ограничения и замечания

- В шаблоне администратор — суперпользователь (так работает `POSTGRES_USER`); приложение и аналитик суперпользователями не являются.
- Репликация асинхронная: при аварии возможна потеря последних записей (в опыте 0). Переключение выполняется командой оператора, но приложение восстанавливает подключение само.
- Шаблон не использует слот репликации: при простое replica дольше, чем вмещает `wal_keep_size = 256MB`, её нужно пересоздать.
- Не выполнялись: PITR и автоматическое переключение без оператора.
- Из ветки удалены миграция ролей с открытым паролем и `backup.dump` в корне репозитория (противоречили требованиям по секретам); пароль остаётся в истории git, см. `secrets.md`.
