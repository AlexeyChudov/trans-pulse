# Работа с секретами

## Правило
Пароли и ключи **не хранятся в git, SQL-файлах, документации и скриптах**. В репозитории лежит только шаблон без значений.

## Где что находится

| Что | Где | В git? |
|---|---|---|
| Шаблон переменных | `lab4/EXPERIMENT-TEMPLATE/.env.example` (значения `change_me_…`) | да |
| Реальные пароли (администратор, приложение, аналитик, репликация, restore-узел) | `lab4/EXPERIMENT-TEMPLATE/.env`, права `600`, случайные значения | **нет** (`.gitignore`) |
| Резервные копии и файл ролей | `lab4/EXPERIMENT-TEMPLATE/backups/` и `*.dump` | **нет** (`.gitignore`) |
| SSL-сертификат и ключ сервера | внутри тома данных контейнера, создаются при инициализации | нет, в репозитории их нет |

## Как это работает
1. `scripts/init_env.sh` создаёт `.env` из шаблона и подставляет случайные пароли (`openssl rand -hex 16`). Существующий файл не перезаписывается.
2. `compose.yaml` берёт значения из `.env` через `${…}` и передаёт их контейнерам; без заполненного `.env` compose не запустится.
3. Роли создаёт скрипт инициализации `primary/init/01-initialize-cluster.sh` из переменных окружения контейнера. В SQL-файлах паролей нет.
4. Демо-скрипты читают `.env`, строку подключения собирают «на лету», пароль в вывод не печатается.
5. Список ролей для восстановления создаётся с флагом `--no-role-passwords`: пароли в резервную копию ролей не попадают.
6. Приложение получает только свой пароль (`APPLICATION_PASSWORD`). Пароль администратора ему не передаётся.

## Что делать при компрометации пароля
1. Сменить пароль роли: `ALTER ROLE course_app PASSWORD '…'` (от администратора) и обновить `.env`.
2. Если пароль попал в git, считать его скомпрометированным: сменить, историю репозитория чистить отдельно.
