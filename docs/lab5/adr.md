# Журнал архитектурных решений (ADR)

Формат записи: контекст → решение → последствия.

## ADR-001. PostgreSQL остаётся источником истины для транзакционных данных; MongoDB — для потока и гибких данных
**Контекст.** Нужно добавить документное хранилище, не превращая его в копию реляционной схемы.
**Решение.** В PostgreSQL остаются пользователи, справочники, рейсы, инциденты (ограничения, транзакции, SQL-аналитика). В MongoDB — телеметрия, журнал событий рейса, заметки расследования, гибкие атрибуты остановок; для остановок и состава маршрутов MongoDB хранит проекцию (источник истины — PostgreSQL). Подробно — `data-ownership.md`.
**Последствия.** Нет двойной записи одних и тех же фактов; общей транзакции между хранилищами нет, поэтому правила между ними проверяет приложение (ADR-010).

## ADR-002. Телеметрия хранится «корзинами» (bucket pattern): один документ на автобус и час
**Контекст.** Поток однотипных GPS-точек; читают всегда диапазоном времени по одному автобусу.
**Решение.** `telemetry_buckets` с встроенным массивом `points` (не более 720), уникальный индекс `(vehicle_id, hour)`, запись — один атомарный upsert с `$push`.
**Последствия.** Документов в сотни раз меньше, чем точек; история читается несколькими документами. При заполнении корзины (720) запись отклоняется с конфликтом — при нормальной частоте 5–10 с этого не происходит. Вариант «документ на точку» отвергнут: огромное число мелких документов и индексов.

## ADR-003. Журнал рейса: события встроены в один документ, `_id` = номер рейса
**Контекст.** Журнал всегда читают целиком с рейсом, дописывают в конец, прошлое не правят.
**Решение.** `trip_journals`, массив `events` не более 500, хронологию и лимит проверяет сам `$push` (фильтр по `last_event_at` и `events.499`).
**Последствия.** Чтение одним запросом без соединений; границу размера подтвердил эксперимент (ADR-011). Один журнал на рейс гарантирует сам `_id`.

## ADR-004. Карточка инцидента: ссылки на PostgreSQL + встроенные комментарии; `_id` = номер инцидента
**Контекст.** Расследование — это заголовок, теги и цепочка комментариев; рейс, автобус, маршрут и люди уже описаны в PostgreSQL.
**Решение.** Документ хранит только идентификаторы-ссылки (`trip_id`, `vehicle_id`, `route_id`, авторы) и встроенные `comments` (не более 200). Закрыть карточку можно только при закрытом инциденте в PostgreSQL.
**Последствия.** Нет устаревших копий чужих данных; подробности рейса при необходимости берутся из PostgreSQL по идентификатору.

## ADR-005. Остановки: проекция из PostgreSQL + гибкие атрибуты + гео-индекс
**Контекст.** Нужен поиск ближайших остановок и у остановок разный набор признаков (укрытие, скамейки, подсветка…).
**Решение.** `stop_points` с GeoJSON-точкой и индексом `2dsphere`; имя и координаты копируются из PostgreSQL при создании, `attributes` принадлежит MongoDB (до 20 значений простых типов).
**Последствия.** Поиск `$geoNear` с расстоянием в метрах; атрибуты не требуют миграций схемы. Цена — проекцию нужно создавать явно (ручной шаг администратора), расхождение имени или координат с PostgreSQL исправляется пересозданием проекции.

## ADR-006. Связь M:N «маршруты ↔ остановки»: ссылки с двух сторон, порядок шагов без транзакций
**Контекст.** Остановка входит в несколько маршрутов, маршрут состоит из многих остановок.
**Решение.** `route_profiles.stops = [{stop_id, seq}]` и `stop_points.route_ids = [route_id]`. Обновление состава маршрута: (1) добавить обратные ссылки у новых остановок (`$addToSet`), (2) заменить профиль, (3) убрать ссылки у выбывших (`$pull`). Все шаги идемпотентны.
**Последствия.** Если сбой случится между шагами, останется лишняя обратная ссылка (безвредно: она лишь не даёт удалить остановку), а не потерянная; повтор операции исправляет состояние. Альтернатива — встроить остановки в маршруты — отвергнута (ADR в `embedding-vs-reference.md`).

## ADR-007. Три уровня защиты данных: схема базы, атомарные фильтры, проверки сервиса
**Контекст.** Одних проверок приложения мало (данные могут попасть в обход него), а схема MongoDB не видит PostgreSQL.
**Решение.** (1) `$jsonSchema` со `strict`/`error` защищает типы, обязательные поля, диапазоны и правила формы документа; (2) условия порядка и лимитов закодированы в фильтре самой операции записи — проверка и запись атомарны; (3) правила, зависящие от PostgreSQL, проверяет сервис. Подробно — `validation.md`.
**Последствия.** Ошибка валидации базы (код 121) переводится в `invalid_input`; тесты вставляют документы мимо приложения и проверяют отказ базы.

## ADR-008. Версия документа в поле `schema_version`, ломающие изменения — по схеме expand → migrate → contract
См. `versioning.md`. Решение принято заранее, хотя пока существует одна версия, потому что документы живут дольше кода.

## ADR-009. CRUD документных данных — в Go REST API, а не в скриптах `mongosh`
**Контекст.** Документная часть должна жить рядом с остальным приложением и под той же авторизацией.
**Решение.** Те же слои (domain → service → repository → http), тот же JWT и те же роли; репозитории MongoDB лежат в `internal/repository/mongo` (пакет `mongorepo`), интерфейсы — в `domain`.
**Последствия.** Сервисы тестируются на фейках без баз, репозитории — на настоящей MongoDB, HTTP — через `httptest`; всё запускается одной командой `make api-test`.

## ADR-010. Многодокументные транзакции не используются
**Контекст.** Учебный стенд — одиночный узел MongoDB, транзакции требуют replica set; к тому же между PostgreSQL и MongoDB общей транзакции нет в любом случае.
**Решение.** Все критичные правила выражены внутри одного документа атомарной операцией; операции между документами идемпотентны и упорядочены так, чтобы сбой был безвреден (ADR-006).
**Последствия.** Допустима кратковременная несогласованность проекции (например, лишняя обратная ссылка), но не потеря данных.

## ADR-011. Границы встроенных массивов выбраны по эксперименту
**Контекст.** Нужно знать, где встраивание перестаёт быть безопасным.
**Решение.** По результатам `cmd/embedgrowth` (жёсткий предел 141 918 событий, мягкий ~9 000) выбраны границы с большим запасом: корзина 720 точек, журнал 500 событий, карточка 200 комментариев. Превышение лимита — это сигнал вынести хвост в отдельную коллекцию, а не поднять лимит.

## ADR-012. Проверка SQL-запросов эталонами, посчитанными вручную
**Контекст.** Эталон, снятый с первого запуска запроса, повторяет и его ошибки.
**Решение.** Для маленького набора данных результаты всех 8 запросов вычислены вручную до запуска (`lab5/sql/expected/`); скрипт `check.sh` сравнивает вывод с ними. Работа проверки подтверждена «мутацией» эталона.
**Последствия.** Совпадение — независимое подтверждение правильности запросов.
