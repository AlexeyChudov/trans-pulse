# Сравнение: JSONB в PostgreSQL и коллекция MongoDB (один сценарий)

**Сценарий:** журнал событий рейса. Один журнал — один рейс, внутри массив событий (прибытие на остановку, задержка, потеря связи, заметка). Те же данные хранятся двумя способами:
- **A. PostgreSQL:** таблица `(trip_id bigint PK, events jsonb, last_event_at timestamptz)`, GIN-индекс `jsonb_path_ops` по `events`.
- **B. MongoDB:** коллекция документов со встроенным массивом `events`, составной индекс `(events.type, events.delay_seconds)`.

Данные генерируются детерминированно (одинаковые в обоих хранилищах): 5 000 журналов по 100 событий, всего 500 000. Программа — `cmd/jsonbvsmongo`, полный вывод — `lab5/results/jsonb_vs_mongo.txt`. Результаты поисков и аналитики программа сверяет между хранилищами автоматически и останавливается, если они расходятся (в прогоне все совпали).

## Результаты (миллисекунды; точечные операции — среднее из 200 повторов, запросы по всем данным — медиана из 5 запусков)

| Операция | PostgreSQL jsonb | MongoDB |
|---|--:|--:|
| Загрузка всех данных | 794 | 717 |
| Размер данных до сжатия | 36 554 КБ | 31 193 КБ |
| Данные на диске (со сжатием, без индексов) | 7 176 КБ | 5 576 КБ |
| Индексы на диске | 6 056 КБ | 512 КБ |
| Прочитать журнал рейса целиком | 0,27 | 0,29 |
| Добавить событие в конец (с проверкой хронологии) | 0,47 | 0,35 |
| Найти журналы с задержкой ровно 600 с (2 040 журналов) | 30,8 | 6,7 |
| Найти журналы с задержкой больше 850 с (3 246 журналов) | 36,7 | 9,3 |
| Аналитика: число событий каждого типа по всем журналам | 85,7 | 73,1 |

## Защита данных

Попытка записать событие `DELAY_DETECTED` без `delay_seconds`:

| Вариант | Результат |
|---|---|
| PostgreSQL jsonb без ограничений | **принято**: структуру внутри jsonb база сама не проверяет |
| PostgreSQL jsonb + `CHECK` с условием на языке jsonpath | отклонено (код 23514), но правило пришлось записать вручную |
| MongoDB со схемой валидации | отклонено (код 121); схема описывается декларативно, включая типы, диапазоны и запрет лишних полей |

Время в jsonb хранится строкой (типа «дата» там нет), а в MongoDB тип `date` проверяется схемой: попытка записать `"at": "вчера"` отклоняется.

## Выводы

1. **Простые операции почти одинаковы.** Чтение журнала целиком (0,27 и 0,29 мс) и добавление события (0,47 и 0,35 мс) — разница в доли миллисекунды. Атомарное добавление в jsonb (`events = events || $1`) с условием хронологии в `WHERE` работает так же надёжно, как `$push` с фильтром в MongoDB.
2. **Поиск внутри массива быстрее в MongoDB** (в 4–5 раз на этих данных: 6,7 и 9,3 мс против 30,8 и 36,7 мс). Индекс по полям внутри массива покрывает и равенство, и диапазон. GIN-индекс `jsonb_path_ops` ускоряет поиск по вложению (равенство), а запрос по диапазону (`delay_seconds > 850`) в jsonb пришлось выполнять функцией `jsonb_path_exists`, которая этот индекс не использует.
3. **Аналитика по всем событиям сопоставима** (86 и 73 мс). Но у jsonb есть сильное преимущество: он живёт рядом с остальными таблицами, поэтому журнал можно соединять с `trips`, `routes`, `vehicles` обычным `JOIN` и применять оконные функции из каталога SQL. В MongoDB такое соединение возможно только копированием данных.
4. **Размер.** На диске данные в MongoDB компактнее (5,6 МБ против 7,2 МБ), индексы — сильно (0,5 МБ против 6,1 МБ), хотя индексы у систем разные по назначению (в PostgreSQL GIN покрывает все вложенные значения).
5. **Целостность и транзакции — аргумент за jsonb.** Журнал в PostgreSQL можно связать внешним ключом с `trips(id)` и менять в одной транзакции вместе с рейсом. В MongoDB наличие рейса проверяет приложение (ADR-001, ADR-010), общей транзакции между хранилищами нет.
6. **Защита данных — аргумент за MongoDB.** Схема валидации декларативна и проверяет типы; в jsonb такие правила — вручную и без типа «дата».

## Что это значит для проекта

Для журнала рейса **jsonb в PostgreSQL — рабочая альтернатива**, особенно если важны единая транзакция с рейсом и аналитика с `JOIN`. В проекте выбрана MongoDB, потому что: журнал и телеметрия — однотипные потоковые данные, для которых нужны индексы по полям внутри массивов, декларативная схема валидации и гео-поиск по тем же документам (`stop_points`), а цель работы — документная модель. Если бы главным требованием стала транзакционная связность журнала с рейсом, правильным выбором стал бы jsonb.

## Ограничения эксперимента

Один узел каждой СУБД на одной машине, 500 тысяч событий, высокая доля совпадений в поисках (40–65 % журналов), поэтому абсолютные числа нужно считать ориентировочными; на больших объёмах и при другой селективности разница изменится. Сравнивались именно jsonb и коллекция MongoDB; классическая нормализованная таблица событий (по строке на событие) в этот замер не входила.
