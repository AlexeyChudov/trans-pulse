# Модель владения данными: PostgreSQL и MongoDB

Принцип: **у каждого факта один источник истины**. Всё, что требует транзакций, ограничений целостности и аналитики с соединениями, остаётся в PostgreSQL. В MongoDB уходят данные, у которых другая природа: поток однотипных записей, события с переменным составом полей, заметки, гео-поиск.

## Кому что принадлежит

| Данные | Хранилище | Источник истины | Почему |
|---|---|---|---|
| Пользователи, роли, пароли (хэши) | PostgreSQL | PostgreSQL | безопасность, уникальность логинов, внешние ключи |
| Маршруты, остановки, состав маршрутов (`route_stops`) | PostgreSQL | PostgreSQL | справочные данные с ограничениями (BR-02…05), используются в SQL-аналитике |
| Автобусы, рейсы (плановое и фактическое время, статус) | PostgreSQL | PostgreSQL | жизненный цикл, «один активный рейс на автобус» (частичный уникальный индекс), транзакции |
| Инциденты (тип, статус, кто и когда закрыл) | PostgreSQL | PostgreSQL | статус и правила `OPEN → RESOLVED` гарантируются ограничениями БД |
| **Телеметрия** (GPS-точки) | MongoDB `telemetry_buckets` | **MongoDB** | огромный поток однотипных записей, чтение диапазоном по автобусу, в PostgreSQL её нет |
| **Журнал событий рейса** | MongoDB `trip_journals` | **MongoDB** | события разных типов с разными полями, всегда читаются вместе с рейсом |
| **Заметки расследования инцидента** (заголовок, теги, комментарии) | MongoDB `incident_cases` | **MongoDB** | свободный текст и теги; статус самого инцидента остаётся в PostgreSQL |
| Атрибуты остановок (укрытие, скамейки…) | MongoDB `stop_points.attributes` | **MongoDB** | набор атрибутов разный у разных остановок, схема гибкая |
| Копия остановки (имя, координаты) для гео-поиска | MongoDB `stop_points` | PostgreSQL | **проекция** для запросов `$geoNear`; при расхождении верна запись в PostgreSQL |
| Состав маршрута (упорядоченные остановки) для чтения | MongoDB `route_profiles` + `stop_points.route_ids` | PostgreSQL (`route_stops`) | проекция для быстрого чтения; связь M:N хранится ссылками с двух сторон |
| Текущее положение автобусов | Redis (в этой работе не реализуется) | Redis | краткоживущее оперативное состояние (решение из ЛР1) |

## Правила, связывающие хранилища

1. **Ссылки только по идентификаторам.** Документ MongoDB хранит числовой `id` из PostgreSQL (`trip_id`, `vehicle_id`, `route_id`, `author_id`) и не копирует чужие данные, которые могут измениться. Для документов «один к одному» `_id` документа равен `id` в PostgreSQL (`trip_journals._id = trips.id`, `incident_cases._id = incidents.id`): уникальность гарантируется самим ключом.
2. **Создавать документ можно, только если родитель существует в PostgreSQL.** Журнал создаётся для существующего рейса, карточка — для существующего инцидента, телеметрия — для существующего автобуса (BR-09), проекция остановки — для существующей остановки. Проверку выполняет сервис перед записью в MongoDB.
3. **Правила статусов берутся из PostgreSQL.** Карточку инцидента нельзя закрыть, пока инцидент не закрыт в PostgreSQL. В журнал отменённого рейса писать нельзя.
4. **Проекции обновляются только в сторону «PostgreSQL → MongoDB».** Имя и координаты остановки копируются при создании проекции; в MongoDB их вручную не меняют. Расширенные атрибуты остановки (`attributes`) принадлежат MongoDB и в PostgreSQL не пишутся.
5. **Удаление родителя не каскадируется автоматически.** В PostgreSQL рейсы и инциденты не удаляются физически (ON DELETE RESTRICT, логическое отключение), поэтому «висячих» документов не появляется; удаление самого документа MongoDB (журнал, карточка) — отдельная административная операция.

## Согласованность без транзакций между хранилищами

Общей транзакции PostgreSQL ↔ MongoDB нет. Поэтому:
- запись в PostgreSQL и запись в MongoDB — это **разные операции**, между которыми допустим сбой; приложение устроено так, чтобы вторая операция была безопасна при повторе (`$addToSet`, `$pull`, upsert, проверки статуса в фильтре);
- для связи M:N порядок шагов выбран так, чтобы сбой посередине оставлял безвредную «лишнюю» ссылку, а не «потерянную» (см. ADR-006);
- кластер MongoDB в учебной среде — одиночный узел, многодокументные транзакции недоступны (нужен replica set); все критичные правила внутри одного документа выполняются атомарно одной операцией записи.

## Какие задачи выигрывают от документной модели

| Задача | Почему документная модель лучше |
|---|---|
| Приём и чтение GPS-телеметрии | тысячи однотипных точек в секунду; корзина «автобус + час» с встроенным массивом уменьшает число документов в десятки раз и читается диапазоном одним запросом |
| Журнал событий рейса | события разных типов (прибытие, задержка, потеря GPS, заметка) с разными полями; журнал всегда читается целиком вместе с рейсом — встроенный массив даёт чтение одним запросом без соединений |
| Карточка расследования инцидента | заголовок, теги, цепочка комментариев — естественно один документ; в реляционной модели это три таблицы и соединения |
| Поиск ближайших остановок | встроенный гео-индекс `2dsphere` и `$geoNear` с расстоянием в метрах |
| Гибкие атрибуты остановок | у разных остановок разные наборы признаков, не нужны миграции схемы |

Где документная модель **не** нужна, и данные остаются в PostgreSQL: справочники с ограничениями, жизненный цикл рейсов, статусы инцидентов, аналитика с группировками и оконными функциями (каталог из 8 запросов).
