# Стратегия изменения версии документа

Документы в MongoDB живут долго, а их форма со временем меняется. Чтобы изменения не ломали работающее приложение и уже сохранённые данные, у каждого документа есть поле `schema_version` (сейчас везде `1`), а схема валидации перечисляет допустимые версии.

## Что считается изменением версии

| Изменение | Новая версия? | Пример |
|---|:-:|---|
| Добавить необязательное поле | нет | `severity` в карточке инцидента: старые документы остаются корректными |
| Добавить значение в `enum` (новый тип события) | нет | `TELEMETRY_RESTORED` |
| Сделать поле обязательным, переименовать, сменить тип или единицы измерения | **да** | `delay_seconds` → `delay_ms`; `at` из строки в дату |
| Изменить смысл поля | **да** | поле `status` стало означать другое |

## Порядок выпуска ломающего изменения (expand → migrate → contract)

1. **Расширить схему.** Валидатор допускает обе версии: `schema_version ∈ {1, 2}` и два варианта формы документа (`oneOf`). Применяется через `collMod` при старте новой версии приложения (`EnsureSchema`).
2. **Выкатить приложение, которое понимает обе версии:** читает v1 и v2, пишет только v2. На этом шаге откат приложения безопасен, потому что база по-прежнему принимает старую форму.
3. **Перенести данные фоном.** Скрипт обновляет документы пачками (`updateMany` по диапазону `_id` с фильтром `schema_version: 1` и конвейером обновления: `$set`, `$unset`, `$multiply`). Свойства скрипта: безопасен при повторном запуске (уже перенесённые документы фильтр не выбирает), есть режим «пробного запуска» (только подсчёт), пачки небольшие, чтобы не блокировать запись, перед стартом делается резервная копия коллекции.
4. **Проверить.** Число документов с `schema_version: 1` равно нулю; выборочное сравнение значений до и после (например, секунды × 1000 = миллисекунды).
5. **Сузить схему.** Валидатор допускает только v2, из кода удаляется чтение v1. Старое поле удаляется в этот момент, а не раньше: пока оно есть, миграцию можно откатить.

## Правила

- Версия — целое число, растёт на единицу; пропускать версии нельзя (v1 → v3 только через v2).
- Новая версия не должна одновременно менять несколько несвязанных вещей.
- Версия записывается приложением при создании документа (`schema_version: 1` ставит репозиторий), а миграция повышает её вместе с данными.
- Читающий код никогда не предполагает, что в коллекции все документы одной версии, пока не завершён шаг 5.

## Пример

Журнал рейса: в v2 решено хранить задержку в миллисекундах (`delay_ms`) вместо секунд (`delay_seconds`).
- Шаг 1: схема события допускает `delay_seconds` (v1) или `delay_ms` (v2).
- Шаг 3: `updateMany({schema_version: 1}, [{$set: {schema_version: 2, events: {$map: {…delay_ms: {$multiply: ["$$e.delay_seconds", 1000]}…}}}}])` по пачкам.
- Шаг 5: схема допускает только `delay_ms`, `delay_seconds` удалено.

Эта стратегия описана, но не применялась: в проекте пока одна версия схемы (v1). Все документы создаются с `schema_version: 1`, и схема отклоняет любое другое значение.
