# Настройки schema validation и бизнес-правила

## Настройки

Для всех пяти коллекций применяется валидатор `$jsonSchema` с параметрами:

| Параметр | Значение | Смысл |
|---|---|---|
| `validationLevel` | `strict` | проверяются и вставки, и обновления любых документов |
| `validationAction` | `error` | документ, нарушающий схему, не записывается |

Схемы описаны в `internal/repository/mongo/schema.go` и применяются при каждом запуске приложения (`EnsureSchema`): новая коллекция создаётся командой `createCollection` с валидатором, существующая обновляется командой `collMod`. Так схема в базе всегда совпадает с кодом.

Посмотреть настройки на живой БД:
```
db.getCollectionInfos({name: "trip_journals"})[0].options      // validator, validationLevel, validationAction
db.getCollection("trip_journals").getIndexes()
```

## Что проверяет схема (во всех коллекциях)

- **Типы:** идентификаторы — целые (`int`/`long`), время — `date`, числа — `number`, строки — `string`; ошибка типа (например, время строкой) отклоняется.
- **Обязательные поля:** см. `dictionary.md`, столбец «Об.».
- **Запрет лишних полей:** `additionalProperties: false` у документа и вложенных элементов.
- **Диапазоны и длины:** `minimum`/`maximum`, `minLength`/`maxLength`, `maxItems`, `uniqueItems`, `maxProperties`.
- **Версия схемы:** `schema_version` допускает только известные значения (сейчас 1).

## Бизнес-правила

| № | Правило | Где обеспечивается |
|---|---|---|
| 1 | Широта −90…90, долгота −180…180 (BR-10, BR-11), скорость 0…250, время измерения обязательно (BR-12) и не из будущего | схема (диапазоны, `required`) + сервис `TelemetryService.Record` |
| 2 | Телеметрию принимает только существующий автобус (BR-09); период истории не больше 24 часов | сервис (проверка в PostgreSQL) |
| 3 | Поля события журнала зависят от типа: `DELAY_DETECTED` требует `delay_seconds`, `ARRIVED_AT_STOP` — `stop_id`; другим типам эти поля не нужны | схема (`oneOf` по типу события) + сервис |
| 4 | События журнала идут в хронологическом порядке; в журнале не больше 500 событий | **атомарный фильтр** операции `$push` (`last_event_at`, `events.499` не существует) — проверка и запись одной операцией, гонки невозможны |
| 5 | В журнал отменённого рейса писать нельзя; журнал — только для существующего рейса, один на рейс | сервис (проверка в PostgreSQL) + `_id` = номер рейса |
| 6 | Закрытая карточка обязана иметь `closed_at` и `closed_by`, открытая — не иметь их | схема (`oneOf` по статусу) |
| 7 | В закрытую карточку нельзя добавлять комментарии и менять её; комментариев не больше 200 | атомарный фильтр обновления (`status: OPEN`, `comments.199` не существует) |
| 8 | Карточку можно закрыть, только когда инцидент закрыт в PostgreSQL (источник истины статуса) | сервис `CaseService.Close` |
| 9 | Нумерация остановок маршрута строго 1…N без пропусков и повторов; остановка не повторяется; у каждой остановки есть проекция | сервис `GeoService.SetRouteStops` + схема (`seq ≥ 1`) |
| 10 | Остановку, входящую в маршруты, удалить нельзя | атомарный фильтр удаления (`route_ids` пуст) |

Правила, нарушение которых невозможно «обойти» в обход приложения (типы, диапазоны, правила 3 и 6), защищены схемой базы. Правила, зависящие от PostgreSQL (2, 5, 8), проверяет сервис, потому что схема MongoDB не может обращаться к другой базе.

## Проверка

- Репозиторные тесты (`internal/repository/mongo/schema_test.go`) вставляют документы **в обход приложения** и убеждаются, что каждый недопустимый документ отклоняется базой с кодом 121 (`DocumentValidationFailure`), а допустимый проходит: 31 негативный случай.
- Остальные правила — тесты сервисов и репозиториев; живая проверка — `scripts/api_smoke.sh` (раздел MongoDB).
