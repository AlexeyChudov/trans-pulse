Проект: система мониторинга общественного транспорта (`trans-pulse`). Схема БД та же, что в ЛР2 (7 таблиц, миграции не менялись). Работа выполнена на отдельной базе `trans-pulse_lab3` (PostgreSQL 16 в Docker).

# 1. Генератор данных и запуск

Генератор написан на Go (`cmd/gen`), загружает данные через `COPY`. Детерминирован: фиксированный `seed` (по умолчанию 42) и фиксированная «текущая дата» (01.10.2026). Проверено: два запуска с seed 42 дают одинаковую контрольную сумму таблиц `trips` и `incidents`, seed 7 даёт другие данные.

**Запуск:**

1. `docker compose up -d` — поднять PostgreSQL.
2. `make lab3-db` — создать БД `trans-pulse_lab3` и применить миграции.
3. `make gen-dev` — режим разработки; `make gen-load` — режим нагрузки.
4. `make lab3-stats` — статистика распределения.
5. Запросы: `lab3/sql/queries/q1..q5`; сценарии: `make lab3-race`, `make lab3-deadlock`, `make lab3-loadbench`.

# 4. Многошаговая транзакция

Сценарий «вывести автобус из эксплуатации» изменяет три таблицы в одной транзакции:

1. `vehicles`: статус автобуса → `OUT_OF_SERVICE`;
2. `trips`: все его запланированные рейсы → `CANCELLED`, активный рейс → `COMPLETED` с фактическим временем окончания;
3. `incidents`: открытые инциденты активного рейса → `RESOLVED` с указанием диспетчера.

Для автобуса 1 (было: `IN_SERVICE`, 442 запланированных рейса, активный рейс, 1 открытый инцидент):

| Состояние | Автобус | Запланированных рейсов | Активный рейс | Открытых инцидентов |
|---|---|--:|---|--:|
| Исходное | `IN_SERVICE` | 442 | `IN_PROGRESS` | 1 |
| В транзакции после шагов 1–3 | `OUT_OF_SERVICE` | 0 | `COMPLETED` | 1 |
| После **ROLLBACK** (шаг 4 с несуществующим `user_id = 9999` нарушил `fk_incidents_resolved_by`) | `IN_SERVICE` | 442 | `IN_PROGRESS` | 1 |
| После **COMMIT** (шаг 4 с существующим пользователем) | `OUT_OF_SERVICE` | 0 | `COMPLETED` | 0 |

Откат вернул все три таблицы в исходное состояние, фиксация применила изменения целиком.

# 5. Конкурентное выполнение

**Бизнес-правило BR-07:** один автобус не может одновременно выполнять два активных рейса. Два диспетчера одновременно запускают два разных запланированных рейса автобуса 9 (схема «проверить, подождать 1 с, записать»).

| Вариант | Что произошло | Итог |
|---|---|---|
| A. Проверка в приложении, защиты в БД нет (индекс снят) | Обе сессии увидели 0 активных рейсов, обе выполнили `UPDATE` и `COMMIT` | **2 активных рейса — правило нарушено** |
| B. Та же логика, индекс `uq_trips_one_active_per_vehicle` есть | Вторая сессия получила `23505` (нарушение уникальности) и откатилась | 1 активный рейс |
| C. Блокировка строки автобуса (`SELECT … FOR UPDATE`), индекса нет | Вторая сессия ждала 1 с, затем увидела 1 активный рейс и штатно отказалась (без ошибки БД) | 1 активный рейс |

Вывод: надёжная защита — частичный уникальный индекс как «последний рубеж»; `FOR UPDATE` дополнительно даёт понятный бизнес-отказ вместо ошибки БД. Индекс после эксперимента восстановлен.

# 6. Оптимизация запросов

Выбраны Q1 (маршруты и опоздания) и Q2 (открытые инциденты). Замер: 7 запусков `EXPLAIN (ANALYZE, BUFFERS)` до и после, берётся медиана; «до» и «после» сняты подряд на одной машине. Планы сохранены в `lab3/explain/`.

| Запрос | Что добавлено | Медиана до, мс | Медиана после, мс | Ускорение | План до → после |
|---|---|--:|--:|--:|---|
| Q1 | покрывающий индекс `trips (status, planned_start) INCLUDE (route_id, actual_start)`, 168 МБ | 192,0 | 59,7 | 3,2× | Parallel Seq Scan по 3 млн рейсов → Parallel Index Only Scan по диапазону сентября |
| Q2 | частичный индекс `incidents (type, created_at DESC) WHERE status = 'OPEN'`, 64 КБ | 18,9 | 0,24 | ≈80× | Parallel Seq Scan по 257 тыс. инцидентов → Index Scan по индексу в нужном порядке, остановка после 10 строк (LIMIT) |

Пояснения:
- **Q1.** Без индекса приходилось читать всю таблицу (~40 тыс. страниц, из них ~31 тыс. с диска/кэша ОС) и отбрасывать 92% строк. С индексом читается только нужный диапазон, обращений к таблице почти нет (2 437 при 225 тыс. строк), физических чтений нет. Число обращений к буферам не уменьшилось (≈47 тыс., все из кэша), выигрыш получен за счёт отсутствия чтений с диска и более дешёвой обработки строки. Цена: +168 МБ хранилища (около 40% от размера таблицы `trips` с индексами).
- **Q2.** Открытые инциденты составляют ~0,5% таблицы. Частичный индекс содержит только их, уже отсортированных по `created_at`, поэтому не нужны ни сканирование таблицы, ни сортировка: достаточно прочитать 39 записей индекса.
- Скрипты индексов вынесены отдельно (`lab3/sql/optimize.sql`) и не входят в миграции, чтобы не менять согласованную схему ЛР2.

# 7. Эксперименты повышенного уровня

## 7.1. Сравнение стратегий массовой загрузки (желательно)

Загрузка 50 000 строк в таблицу `trips` без индексов и внешних ключей, 3 прогона, медиана:

| Стратегия | Время, с | Строк/с |
|---|--:|--:|
| `INSERT` по одной строке (autocommit) | 9,06 | 5 521 |
| `INSERT` пачками по 1000 в одной транзакции | 0,36 | 137 724 |
| `COPY` | 0,06 | 865 886 |

`COPY` быстрее построчной вставки примерно в 157 раз, быстрее пачек в 6 раз. Причины: построчная вставка делает отдельный сетевой обмен и фиксацию на каждую строку, пачки убирают лишние обмены и фиксации, `COPY` передаёт данные потоком в одном запросе. Размер таблицы одинаков (≈5,2–5,4 МБ). Поэтому генератор использует `COPY`.

## 7.2. Ожидание блокировки (желательно)

В варианте C (п. 5) пока первая сессия держит блокировку строки автобуса, вторая ожидает её. Диагностика во время ожидания (через 0,5 с):

| Источник | Результат |
|---|---|
| `pg_stat_activity` | сессия `pid=268`: `wait_event_type = Lock`, `wait_event = transactionid`, заблокирована процессом `267`, запрос `SELECT id FROM vehicles WHERE id=$1 FOR UPDATE` |
| `pg_locks` (`granted = false`) | `locktype = transactionid`, `mode = ShareLock` — ожидание завершения транзакции процесса 267 |
| `pg_blocking_pids()` | `{267}` — идентифицирует блокирующий процесс |

Ожидание закончилось через ~1 с, когда первая сессия выполнила `COMMIT`.

## 7.3. Deadlock (восхитительно)

**Воспроизведение.** Две транзакции переносят рейсы между автобусами 3 и 4. T1 блокирует строку автобуса 3, затем 4; T2 — автобус 4, затем 3. Через 0,5 с каждая ждёт строку, удерживаемую другой.

**Диагностика.** Через 1 с (параметр `deadlock_timeout`) PostgreSQL обнаружил цикл ожидания и прервал T1 с `SQLSTATE 40P01`. В логе сервера записано: процесс 271 ждёт `ShareLock` на транзакции 1060, которую держит процесс 272, а процесс 272 ждёт транзакцию 1059 процесса 271; указаны запросы обоих процессов (`SELECT … FOR UPDATE` по `vehicles`). T2 после этого завершилась успешно.

**Причина:** разный порядок захвата блокировок в двух транзакциях.

**Устранение:** обе транзакции берут блокировки в одном порядке — по возрастанию `id` автобуса. Повторный запуск: T1 и T2 выполнены последовательно (T2 подождала T1), обе завершились `COMMIT`, ошибок нет.
